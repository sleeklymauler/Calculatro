# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Windows-only project (paths rely on `%APPDATA%`). Use the venv interpreter:

- Setup: `python -m venv .venv; .venv\Scripts\pip install -e ".[dev]"`
- All tests: `.venv\Scripts\python -m pytest`
- Single test: `.venv\Scripts\python -m pytest tests/test_engine.py::test_name`
- Performance: `.venv\Scripts\python tests\perf\benchmark.py` (timings; `-k` filters, `--compare tests\perf\baseline.json`; the "Best discard" scenarios time the search button), and `.venv\Scripts\python -m pytest -m perf` (exact results against the committed `tests/perf/expected.json`, written by `benchmark.py --update-expected`; timings against the git-ignored, per-machine `tests/perf/baseline.json`, measured by `benchmark.py --save tests\perf\baseline.json`, without which a run stops at collection; skipped by a plain `pytest`). See `docs/performance/README.md`.
- Run: the mod starts the app with the game (see below). By hand: `.venv\Scripts\python -m calculatro watch` (`--file` overrides the state file path), which shows the console output. What to calculate is set in game, with the panel's target editor.
- Install the mod into the game: `pwsh scripts/install_mod.ps1` (copies `mod/Calculatro` to `%AppData%\Balatro\Mods`; requires the Lovely injector DLL next to `Balatro.exe`). Re-run after any change to the Lua. It also writes the venv's `pythonw.exe` path to the installed mod's `launch.txt` (skip with `-NoAutoStart`): on its first frame the mod starts `pythonw -m calculatro watch --game-pid <pid>` through LuaJIT's FFI (`ShellExecuteW`; `os.execute` would flash a console). With `--game-pid` the app exits when the game does (`process.exited`), exits at once if another instance holds the `Local\Calculatro` mutex (`process.claim_instance`; every `watch` claims it; one started by hand beside another only prints, leaving the odds file to the first, since two writers would clash over it), and logs errors to `%AppData%\Balatro\calculatro.log`.

No runtime dependencies; `pytest` and `lupa` are dev-only. There is no linter configured.

## Architecture

Two halves connected by two JSON files:

1. **Lovely mod** (`mod/Calculatro/`): `lovely.toml` registers `calculatro.lua` as a module, patches `Game:update` to call it every frame, and `Controller:key_press_update` for the panel's hotkey (`C`). The module throttles itself to ~5 snapshots/sec, serializes Balatro's global `G` with its own JSON encoder, and writes `%AppData%\Balatro\calculatro_state.json` only when the output changes (write to `.tmp`, remove, rename — the Python reader tolerates the file briefly missing). Each written snapshot gets an `id` (`<session>:<seq>`).
2. **Python app** (`calculatro/`): `source.py` polls the file's mtime/size → `state.py` parses it into frozen `GameState`/`Card` dataclasses → `engine.py` computes exact odds → `report.py` collects them into a `Report` → `__main__.py` formats it for the console and `overlay.py` for the mod. `__main__.run_watch` runs the odds in a `worker.Job` (daemon thread): each new state cancels the running job (the engine checks the `cancel` Event and raises `engine.Cancelled`), and odds slower than ~0.25 s print the summary first with "Calculating odds..." and follow when ready. Keep new slow code paths cancellable. Best-discard searches run in a second job (see 5.), cancelled only when `search_basis` changes.
3. **Odds panel**: the app answers each snapshot in `calculatro_odds.json` (same directory, atomic `os.replace`) — first `{id, pending: true}`, then the odds, echoing the snapshot's `id`. `overlay.write` returns False rather than raising if the file stays locked; `run_watch` then resends the latest payload every `RETRY` seconds until it's written or a newer one replaces it. The mod reads it ~20×/sec with a small JSON decoder and draws a Balatro `UIBox` right-aligned above `G.deck` and high enough to clear the raised hand (`panel_lift`), rebuilt only when its model changes. Its height is capped by the consumables' count label (`max_panel_height`, measured from the label's own UIBox, `G.consumeables.children.area_uibox`, once it exists): target hands and drawn-card queries are separate sections, each filling columns of its own under its own header ("Hands  Keep  Discard" / "Drawn cards  Discard"), so "Keep" never sits over cards. It's built with each section in one column, then one fewer row per column, and so on until it fits, so each column is filled as far as fits before the next starts (6 rows in game), growing leftwards over the play area (empty while selecting). At most 3 columns (`max_columns`; a 4th reaches the HUD sidebar) of 6 rows fit, so the mod won't track targets + card queries needing more (`Calculatro.columns_needed`, mirrored by `overlay.columns_needed`, `ROWS_PER_COLUMN`, `MAX_COLUMNS`, which the app also enforces; "Any target" adds a hand row when there are several targets); keep both in step if the panel's sizes change. Card names span the hands' name, Keep and search-button widths (`CARD_ROW_NAME_W`; `CARD_NAME_W` without the button, as in the editor), since text wider than its cell is shrunk. The Keep→Discard arrow (`arrow`) is drawn as boxes the size of the font's pixels (`FONT_PX`, 0.02 units at the panel's text scale), since a text `->` is too wide for its gap and would be shrunk. Target rows split the gap and the Discard cell differently from the header: `DISCARD_VALUE_W` just fits the widest value (">99.9%"), and the arrow sits in the rest (`ARROW_CELL_W`), midway between the Keep value and a typical one ("88.3%"). The panel draws its own shadows (`deepen_shadows`, on the built UIBox's elements): the game drops text shadows 0.5 parallax units away, nearly invisible on the dark inset, and box shadows 1.5. Text and the arrow both use `SHADOW_DEPTH` instead. The mock `UIBox` has no `UIRoot`, so this isn't covered by the tests. The message ("Calculating...", "Waiting for app") must never change the panel's size, or the columns would flip as it comes and goes: beside the odds it sits on the title row in a space kept for it whether or not there's one (`MESSAGE_W`, so messages there must be short); only with nothing tracked ("Nothing tracked") does it get a row of its own. There's deliberately no hint to select cards, and no "No discards left" (the game shows that). The frame takes the boss's colours like the HUD, but the inset behind the odds is always dark (`inset_colour`, what `BOSS_MAIN` is outside boss blinds): `BOSS_MAIN` is the raw boss colour, too light for the text on bosses like The Club and the same hue as the green/red values on others. Header/footer text uses solid `G.C.JOKER_GREY` and stale values `G.C.UI.BACKGROUND_INACTIVE`, since the translucent `TEXT_INACTIVE` disappears on some boss colours. Long hand names are shortened in `SHORT_NAMES` (Lua). Odds whose `id` isn't the latest snapshot's are still shown, greyed with "Calculating..." after 0.3 s; with no reply at all for 2 s it says it's waiting for the app; odds from another game session are ignored. The panel only exists in a blind (`Calculatro.in_blind`: `SELECTING_HAND`/`DRAW_TO_HAND`, or `PLAY_TAROT` interrupting one, and no `G.OVERLAY_MENU`); it's hidden while a played hand scores (`HAND_PLAYED`), since the played cards reach it. Rebuilds are animated (`Calculatro.animate`, run on the final box in `refresh_panel`): elements tagged `config.calculatro_anim` (the frame, body, inset, title row, each odds row by key, headers by section and column, the editor's rows) are matched by key between the old and new box; matched ones move and resize from where the old box drew them (`drawn_layout`, so a rebuild mid-animation carries on, and a move whose destination is unchanged, as when only the odds change, isn't restarted), new ones pop in afterwards, slightly staggered, and a panel that appears pops in whole. Untagged elements follow the nearest tagged one around them; removed ones vanish. It's done only while drawing (the box's `draw` is replaced), by adjusting each element's `VT` and putting it back after, so layout, collision and buttons see only the final places. Give new panel rows a unique `calculatro_anim` key, or they'll move with their column/inset instead of gliding. It's off with the game's Reduced Motion setting. `tests/test_animation.py` runs it on hand-built element trees. The UI must work on standard 16:9 screens as well as ultrawide: Balatro lays everything out in a fixed 20×11.5-unit room scaled to the window, so place UI relative to game objects in those units, never in pixels or relative to the window edges. Python sends display-ready values (`overlay.percent`), but the mod names the rows itself, since it owns what's tracked and shows rows before the app has answered: each odds row carries a `key`, the hand's name ("Three of a Kind", "Any target") or the card query's text, and the panel shows a row per tracked target with the odds for its key ('-' until there are some). Balatro's font (m6x11) has no suit symbols, arrows or ≤/≥, so panel text must be ASCII (draw anything else, like the arrow and the `x` (`glyph`)), except for ♠♥♣♦ in card query labels (e.g. "Q♠: 1+"): the mod's `name_label` draws those as the game's own suit icons, sprites from the `ui_1` atlas (`ui_2` with the colourblind option) at `{x, y = 1}`, as in the View Deck screen, each on a small white tile so the black suits show on the dark inset.

4. **Targets** are set in game and owned by the mod: `Calculatro.tracked()` keeps `{hands = {names in HANDS order}, cards = {{query, label}}}` on `G.GAME.calculatro`, so the game saves them with the run and a new run starts empty; the snapshot sends them as `tracked` (`GameState.tracked_hands`/`tracked_cards`), and `__main__.tracked` validates them (unknown or repeated ones and any past the column limit are skipped). Each odds row has an `x` to stop tracking it (not "Any target"). The `+` after the title opens the **target editor** (`editor_model`/`editor_definition`), which replaces the odds in the same frame until Done: a Hands tab of 12 toggles and a Cards tab whose option cycles (`OPTIONS`, `Calculatro.builder`) build a query string `cards.parse_query` accepts plus its label (`builder_query`, matching how the app names queries; Python stays the only parser), and the tracked queries 5 to a page. `+`, toggles and Add are greyed and inert when another wouldn't fit. Buttons are `C` nodes with `button = 'calculatro_button'` (`G.FUNCS`, set each frame) and the action in `config.calculatro_action`, dispatched by `Calculatro.act`; the panel UIBox has `can_collide = true` for them. They don't shake the screen: `steady_buttons` gives each a `click` that undoes the `G.ROOM.jiggle` the game's `UIElement:click` adds (the click sound stays). Buttons need a box that isn't replaced while they're used, so the editor is rebuilt only when its own model changes (its buttons), never by odds; it closes when the panel goes away. The editor's tabs take the header's place, but its toggles and option cycles have `TEXT_PAD` above and below their text (`padded`), since m6x11's descenders hang below a text node's box; that makes it taller than the odds panel with 6-row columns, so `refresh_panel` lowers it by whatever doesn't fit under the consumables, into the room kept for raised cards. Both tabs are the same size: `EDITOR_W` is the Cards tab's width worked out from its cells and paddings, and the Cards tab is given the Hands tab's height (`EDITOR_H`, from `TEXT_H`, a text node's exact height in the game's layout). Add and the page cycle share a row under the builder and the list, so Add fits the longest label (`ADD_W`; the game shrinks wider text but not the suit icons) and the page cycle doesn't move between pages.
5. **Best discard**: each target-hand row (including "Any target", not card queries) has a green search button (`search_cell`, a `MAGNIFIER` `glyph`, in a `SEARCH_W` column before the `x`; card rows' names take that width too, `CARD_ROW_NAME_W`). Clicking it sends `search = {key, nonce}` with the next snapshot (`Calculatro.request`, sent with every snapshot; the app acts on each nonce once) and remembers the hand's card objects (`Calculatro.searching`); the button is dimmed and inert and the title row says "Searching..." until the reply. `run_watch` runs `search.best_discards` for the row's target (`__main__.search_target`) in a job of its own, cancelled only when the hand, deck, jokers, blind or discards change (`search_basis` ignores the selection, so the search's own selection doesn't cancel it), and puts its result (`overlay.search`: every tied option as 0-based hand indices, best first; no options for an untracked key) on every payload until then. The mod applies a reply only if its nonce is the one asked for and the hand is still the same card objects in the same order (`receive_search`), selecting the first option (`Calculatro.select`: `unhighlight_all`, which leaves Cerulean Bell's forced card selected, then `add_to_highlighted` with one click sound). Clicking again cycles through the options (`Calculatro.found`) while the hand is the same: the next if the selection is still the last one made, else the first. The title row shows "i/n" with several options and "Keep hand" when keeping is the only best; "Calculating..." and "Waiting for app" take priority. Buttons are inert outside `SELECTING_HAND`, or with no way left to throw cards away before the last hand (`search.can_redraw`/`Calculatro.can_search`: a discard, or a hand played as one with another left after it). There's no cap on tied options for now (a hand that already has a Pair ties on dozens of discards); revisit if it's a nuisance in play. `docs/best-discard/README.md` has the plan it was built from.

### Contract between the halves

- `SCHEMA` in `state.py` must match `schema` in `calculatro.lua`, and `overlay.SCHEMA` must match `odds_schema`; bump both sides when changing either JSON shape. A snapshot of another schema (the previous version's file at startup, or a mod not reinstalled after an update) raises `state.SchemaMismatch`, which `FileStateSource.poll` skips with one message on stderr until the file changes, rather than stopping the app. The odds file never contains `null` (the Lua decoder doesn't support it). The snapshot also sends `select_limit` (`G.hand.config.highlighted_limit`) and the latest `search` request; the odds file's `search` answers it (see 5.).
- Information hiding is deliberate: the deck is exported as a **sorted multiset** so draw order never leaks, and the jokers sorted too (Amber Acorn shuffles them face down), and face-down hand cards are exported as `{hidden: true}` with their identities only in a separate sorted `hidden_pool`. The engine treats `hidden_pool` cards as part of the unseen pool (same as undrawn deck), except that under The Mark (`GameState.mark`) they're known to be face cards, so they're drawn from the unseen face cards (`engine._mark_split`). Don't add anything to the export that reveals information a player couldn't see.
- Empty Lua tables can arrive as `{}` rather than `[]`; the encoder tags arrays with an `ARRAY` metatable, and `state._cards` also handles it.
- Card fields mirror Balatro internals: `rank_id` 2..14 (Ace=14), `enhancement` is the center key (`m_stone`, `m_wild`, `c_base`, ...).

### Probability model

- `hands.py` expresses each poker-hand target as OR-of-patterns, each pattern an AND of `Requirement`s ("at least `need` cards whose class key is in `keys`"). Requirements are usually disjoint; they may overlap (a card then counts towards each). Class keys are `(rank_id, suit)` with suit `"Wild"` for wild cards; with Smeared, Diamonds are keyed as Hearts and Clubs as Spades, and flush-type patterns use only those two suits (`flush_suits`). Containment follows Balatro's rules (Straight Flush contains Straight; Four of a Kind does *not* contain Two Pair). Stone/hidden cards have no key; a debuffed Wild loses wildness. `combine()` builds an "any of these targets" Target, pruning implied patterns.
- `engine.probability()` is exact (`Fraction`), not Monte Carlo: pool cards are merged into classes by which requirements they count toward, then enumerated class-by-class hypergeometrically with early-accept (satisfied ⇒ binomial of remaining), pruning of unreachable patterns, and memoization on a canonical key of what the live patterns still lack. Only patterns touched by the current class are re-assessed. Targets with patterns of several suits are split by suit with inclusion-exclusion (`_union_by_suit`), so each search tracks one or two suits instead of all four; this is skipped when an unseen card is Wild, which links the suits again. Terms that are the same up to relabelling suits (same ranks kept and unseen, e.g. a fresh deck in The House) are computed once. See the module docstring and `docs/performance/` (design notes, per-joker notes, benchmark tables) before modifying, and add benchmark scenarios to `tests/perf/scenarios.py` for new joker rules.
- How a pattern is stated drives the search's size: it memoizes on what each live pattern still needs, so prefer requirements that leave little to remember. Four Fingers' Straight Flush says "a suited card of another rank" rather than "4 suited cards in all", so the search tracks whether a suit has shown up rather than its count, and runs sharing their 3 suited ranks are one pattern ("any card that completes the run"). Classes are swept rank by rank (Wild Cards first in their rank), or suit by suit when no requirement spans several suits; the order patterns are listed in doesn't matter. A pattern joins the search at its first single-rank class; draws before that towards its other requirements are deferred counts in the memo key. In the search, a pattern's state is an interned "part" (unmet requirements as bitmask of remaining classes + deficit), moved past each class by a cached transition; parts implied by a one-card part are dropped from the state.
- `cards.py` parses card queries (`"2+ queens"`, `"at most 1 spade"`, `"QS"`; the editor writes them as `"at least 2 lucky queen of spades"`) into `CardQuery` (`text` keeps what was parsed, the odds' key); these count only over the newly drawn cards (`engine.evaluate_cards`), whereas targets cover the whole final hand (`engine.evaluate_discard`).
- Joker rules (Four Fingers, Shortcut, Smeared, Pareidolia) live in `rules.Rules`, built by `GameState.rules` from non-debuffed jokers. Pareidolia affects only face-card queries (`cards._is_face`: every non-debuffed card, Stone included), never hand patterns. A `Target` only names hand types; `Target.patterns(rules)` builds (and caches) the patterns for a ruleset, and `card_key`, `probability`, `count_probability` and `CardFilter.test` all take the `Rules`.
- The "discard" scenario uses the cards currently highlighted in game (`GameState.selected`).
- `search.best_discards` compares keeping the hand with every discard (or hand played as one, `can_redraw`) of up to `select_limit` cards (always including Cerulean Bell's forced card), for this discard and draw only, using `evaluate_discard`. It enumerates counts per group of hand cards the target can't tell apart (`_groups`: by which requirements a card's key counts towards, face-down cards together; by class under Cerulean Bell, whose random forced card makes the class matter), then expands the best counts into every distinct tied discard (identical cards collapsed, leftmost first), ordered fewest cards, then lowest ranks thrown away, then leftmost. `tests/test_search.py` checks it against trying every subset. It works out each distinct discard once (`_relabelled`: ranks or suits the target can't tell apart are dropped, and relabelled when the patterns are symmetric), bounds "Any target" by its hands' own odds so few need the exact union, and passes one `engine.Reuse` to every `evaluate_discard` so the engine shares its pool-dependent setup (`_layout`), results and memo between discards (`_search`'s `signature`); see `docs/performance/best-discard.md`. Four Fingers + Shortcut with Straight Flush still takes seconds.
- Boss rules: The Serpent's draws (`GameState.serpent`), The Mark's face-down face cards (`GameState.mark`, `engine._mark_split`) Cerulean Bell's forced card (`GameState.bell`/`forced`, from the hand cards' exported `forced` flag; `hands.forced_patterns`, `engine._bell_after_draw`) and The Hook's 2 random cards thrown away after a play, which applies when the selection has to be played for want of discards (`GameState.hook`, `engine._hooked`/`_after_hook`). The Eye's and The Mouth's banned hands don't change the odds: the mod strikes those targets out in the panel itself (`Calculatro.banned_hands`, read from `G.GAME.blind`). `docs/blinds.md` has the details; a new boss rule must check `blind_disabled` like these.
- `docs/jokers.md` is the joker reference (all 150, with internal keys and the exact game rules for Four Fingers / Shortcut / Smeared / Pareidolia). Use it instead of the wiki, which it corrects from the game's code. `docs/blinds.md` is the same for all 30 blinds (exported as `blind` = `G.GAME.blind.name`, plus `blind_disabled`): which bosses the engine models, which arrive through the exported state, and which it gets wrong.

### Tests

`tests/test_state.py` runs the real `calculatro.lua` inside `lupa` against a mocked `G` and `love.filesystem`, then parses the written file — so mod changes are testable without the game. Extend `MOCK_G` there when exporting new game fields. `MOCK_G` also mocks `UIBox` (recording every box in `BOXES`); `tests/test_overlay.py` checks the panel's text and colours end to end. The game runs LuaJIT (Lua 5.1) while `lupa.LuaRuntime` is newer Lua, so avoid 5.2+ features; to check, run the Lua tests with `lupa.LuaRuntime`/`lupa.LuaError` swapped for `lupa.luajit21`'s.
